# 电话的分段播放与真实延迟

2026-11-02 的第二轮延迟优化。DeepSeek Flash、关闭思考、v19 同理心提示词，以及 MiniMax `speech-2.8-hd / Chinese (Mandarin)_Warm_Bestie` 均保持不变。

## PCM 阶段（PR #22）

此前必须等完整 MP3 合成和解码完毕才开始说话。新浏览器通过 `X-Bread-Audio: pcm-s16le-v1` 请求分段音频；服务端仍先校验完整回复，再让 MiniMax 输出 32 kHz、单声道、16 位 PCM。第一段足够播放时即可开始，后续片段按 AudioContext 时间连续排队。不会播放未经校验的模型 token，也没有追加一个更快但音质更低的语音模型。

首段保留 60 毫秒调度余量，回声参考会拼接并转换到麦克风的采样率。开口打断或挂断会停止所有排队片段，包括尚未播放的声音。浏览器停顿判定从 850 降至 650 毫秒；500 毫秒的句中停顿仍属于同一句，超过阈值后续说的内容沿用已有的拼接与取消机制。

旧浏览器继续收到完整 MP3。省流模式、已识别的 2G/3G 或下行估计不足 1 Mbps 的网络也会在请求前选择 MP3，避免 PCM 带宽造成卡顿；网络信息缺失时使用 PCM，实际跨境抖动仍可能影响播放。设置 `BREAD_PCM_STREAM=off` 并重启服务，可让新浏览器也使用原来的完整 MP3；不需要先让用户更新页面。`BREAD_COMBINED_VOICE=off` 则保留上一轮的分离接口回退。

## 共用的稳定性边界

- 上游 SSE 与浏览器 NDJSON 都检查顺序、类型、大小、请求标识和显式结束事件。最多 4 MiB PCM、512 个事件，断流不会被当作播报成功。
- MiniMax 关闭末尾聚合音频，避免把已播过的声音再播一次。采样率、声道和最终格式需与请求一致。
- 合成异常时停止未播放片段、保留已经校验的文字，等待用户重连；不偷偷再次计费合成。
- 沿用原先的会话版本、取消、准入、去重和熔断。流式语音失败不会绕过回复校验。

## PCM 阶段的测量与检查

优化前，三轮固定合成声音通过公网真实 ASR、模型和 TTS，390px 浏览器中的等待为 **6.815 / 8.094 / 5.203 秒**。模型阶段分别为 **3.652 / 4.998 / 2.144 秒**，波动仍是主要慢项。这些数字是这一时刻的样本，不是长期分位数。

相同高清音色、固定文本的服务器直连对照：

| 请求方式 | 第一轮首音频 | 第二轮首音频 |
| --- | ---: | ---: |
| 完整 MP3 | 1.260 s | 0.870 s |
| 流式 PCM | 0.283 s | 0.262 s |

这里只测合成服务的首音频，未包含转写、模型、浏览器及设备出声。另测 Turbo 的首段为 0.292 / 0.300 秒，没有显示出值得换音色质量的优势，因此继续使用 HD。文字模型流式与非流式的三组交替对照也没有稳定的完整回复延迟优势，本轮未改模型传输或提示词。

候选服务器通过真实 DeepSeek → MiniMax：回复 2.313 秒、首 PCM 3.095 秒、完整链路约 3.260 秒（不含 ASR）。还验证重复请求 409、无会话和跨域请求 403。此数据不等同于公网用户说完到出声。

类型检查、248 项单元/集成测试、生产构建与 54 条生产浏览器流程通过。新增覆盖不完整流、乱序、错请求、格式错误、取消、回声跨片段、所有排队声音停止，以及 390px 浏览器真实 AudioWorklet 的自然打断。浏览器用固定媒体夹具，物理鸿蒙手机、微信、蓝牙与扬声器的实际效果仍需单独观察。

可在自己的配置下复测（真实付费合成样本，不自动重试）：

```sh
node scripts/benchmark-call-latency.mjs --live --origin https://your-host --transport pcm --output .local/pcm-latency
```

报告分别记录文字到首 PCM 与完整音频的时间，并保存 WAV；不能用这个 HTTP 计时替代包含 ASR、停顿检测和播放的完整通话计时。此前完整 MP3 的测量继续保留在 [第一轮记录](call-latency.md)。


## 压缩 MP3 流式播放

PCM 在带宽充足时可以早开始，但每秒约需 512 kb 音频，传输 JSON 后还会增大。实际公网浏览器报告为 3G、1.25 Mbps、RTT 400 ms 时，完整 MP3 回退的三轮等待为 **6.510 / 8.343 / 7.557 秒**；不能把服务器首段快直接说成用户通话快。

曾试着只放宽网络分类：同一公网的三轮为 **6.652 / 4.398 / 6.132 秒**，其中一轮的两个 PCM 片段之间出现 **404 ms 调度空隙**。因此关闭了未合并的 PR #23，没有把这项改动发布。原始慢样本和失败路径保留在本次记录中。

后续采用 **MP3 压缩传输、浏览器逐段解码**。请求头为 `X-Bread-Audio: mp3-chunks-v1`，保留 MiniMax HD、32 kHz 单声道、128 kbps；相对 PCM，音频有效载荷约为四分之一。`mpg123-decoder` 从本网站延迟加载，麦克风许可和开场期间预取，不依赖外部 CDN。每个回合使用独立解码实例，结束或取消后释放。所有片段仍使用同一条可打断的 AudioContext 时间线。

- 不支持 WebAssembly 或解码器初始化失败：收齐同一响应中的 MP3，改由浏览器原生解码；不会再请求一次语音合成。
- 省流模式、2G 或已知下行低于 0.3 Mbps：请求前选择完整 MP3。3G 不再因为标签本身禁用压缩流。
- 服务端 `BREAD_MP3_STREAM=off` 可退回完整 MP3；已有 PCM 页面和旧的完整 MP3 页面仍兼容。
- 音频队列最多 4 MiB；解码后时长最多 65 秒。错帧、乱序、流中断不会被标为成功。
- 固定 MP3 按任意 997 字节分片后，与一次解码得到的 PCM 样本逐个一致。浏览器验证了真实 WASM 解码、自然打断、下一轮恢复和所有排队声音停止。

### 候选验证与局限

服务器上的候选版本通过真实 DeepSeek → MiniMax，首音频 **3.085 秒**，其中模型 **2.215 秒**、冷启动合成首段 **0.816 秒**。不含 ASR、浏览器与公网。

通过 SSH 隧道和本机流式代理连接这个候选，390px 浏览器三次完整通话等待为 **4.960 / 6.444 / 6.409 秒**。TTS 首段为 **0.351 / 0.381 / 0.271 秒**；三次均无片段调度空隙、没有页面异常、播放完恢复倾听且挂断后释放麦克风。这是候选功能检查，**不是公网 HTTPS 的上线后对照**，也未达到稳定五秒内的目标。

另用相同 v19 提示词交替比较两版 DeepSeek Flash 的三个合成情境：当前 `deepseek-v4.1-flash-1017` 完整回复为 **2.434 / 1.353 / 1.831 秒**；`deepseek-v4-flash-0731` 为 **2.083 / 2.152 / 3.653 秒**，没有显示稳定优势，纠正情境也少了一句对处境的回应，因此未换模型。最初在 Anthropic 基址上拼接 `chat/completions` 得到 404，这是测试路径选错，不能据此判断服务不支持该协议。随后按[供应商官方说明](https://docs.wjark.com/maas/getAPIKEY%26URL.html)，使用同一主机的 `/api/v1/chat/completions` 完成八组配对：Anthropic 完整回复中位 2.059 秒、范围 1.418–4.066 秒；OpenAI 中位 1.887 秒、范围 1.338–3.801 秒。OpenAI 只在八组中的三组更快，新增五组并未重复首批优势；因此未据此切换生产协议。两组保留同一个模型、提示词与输出检查。

类型检查、生产构建、**254 项单元／集成测试和 55 条生产浏览器流程**通过。合成语音不能代替鸿蒙真机、微信或物理扬声器测试。模型处理与 ASR 仍会波动，不把流式播放描述成已解决全部延迟。


此命令保存 MP3、完整回复、首音频和完成耗时，仍不包含 ASR、停顿检测或浏览器播放时间。
