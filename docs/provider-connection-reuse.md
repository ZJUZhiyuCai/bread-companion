# 通话连接复用与播放缓冲

2026-11-02。这轮保留 DeepSeek Flash、v19 同理心提示词、完整回复校验和 MiniMax 温暖闺蜜 HD，改动集中在连接与播放。

## 为什么改

连续对话中，两次模型请求常常相隔十几秒。服务器上的 Node 原生 fetch 在三次间隔 7.5 秒的探测中，每次都重建连接。重复的 TCP/TLS 握手使每轮又多等一次网络往返。

另一组公网浏览器基线里，三次说完到播放分别为 **8.167 / 6.157 / 5.797 秒**；第三次回复的两个音频片段之间出现 **1.545 秒**调度空隙。浏览器报告的网络类型没有准确反映这段链路，原有弱网缓冲没有启用。

## 改了什么

Node / SQLite 部署为已配置的文字和语音服务分别保留连接：每个 origin 最多 12 条，空闲最多 60 秒，HTTP/1.1、不启用请求流水线。使用 [Node fetch 的自定义 dispatcher](https://nodejs.org/api/globals.html#fetch)，不替换全局 fetch。服务商主动关闭连接时会重新连接；请求取消和截止时间仍生效。连接复用不缓存回复，也不发后台保温请求；没有新增模型或合成的付费重试。

只有配置中的服务地址可以进入这个连接池，跳转仍被拒绝，HTTP 错误响应也会释放响应体。Worker 继续用它原有的 fetch。设置 `BREAD_PROVIDER_KEEPALIVE=off` 并重启 Node 服务即可停用此项，模型与语音配置不需要变。

播放器同时观察本次转写请求的实际往返开销：浏览器耗时减去本站 `Server-Timing` 的处理耗时。开销达到 250 毫秒时，沿用现有的 500 毫秒起播缓冲；正常链路仍为 200 毫秒。它不会把模型处理慢当作网络慢。短回复在流完成时立即播放，等待缓冲期间仍可开口打断或挂断。这个取舍可能稍晚开始说话，目的是减少一句话中途突然停住。

ASR 的一次有界重试还补全了 HTTP 日期形式的 `Retry-After` 处理。供应商要求稍后再试时，不会立即再次发送音频。

## 服务器配对实测

同一服务器、同一上游、相同六个合成情境，按 AB / BA 交替原生和复用连接请求，每次结束后间隔 7.5 秒。模型、提示词、输出上限保持一致。

| 测量 | 原生连接 | 复用连接 |
| --- | ---: | ---: |
| 三次无鉴权传输探测，中位耗时 | 2.264 s | 0.366 s |
| 上述探测新建连接数 | 3 | 1 |
| 六次模型完整回复，中位耗时 | 2.146 s | 2.005 s |
| 上述模型请求新建连接数 | 6 | 0 |
| 模型回复范围 | 1.943–4.200 s | 1.361–2.779 s |

无鉴权探测返回预期的 405，仅用来检查传输，不代表模型速度。六组模型配对中四组复用方式更快，两组更慢；供应商提示词缓存命中情况也不同，原始记录保留了 usage。因此可以确认连接被复用，**不能把传输探测的下降幅度当成整通提速，更不能承诺稳定五秒以内**。

十二条合成情境回复均通过现有可观察风格约束，覆盖准备后被拒、只想倾诉、纠正和主动请求小建议。它验证本次输出，没有测量心理效果，也不是完整的同理心评分。

## 验证范围

类型检查、生产构建、**287 项单元／集成测试、63 条生产浏览器流程**通过。新增检查覆盖连接重用与服务端关闭、取消后释放连接、不同请求凭据隔离、跳转拦截、错误响应释放、日期冷却，以及浏览器误报为快网时第二音频片段延迟 1.5 秒的播放行为。原有 120 回合 / 40 分钟模拟连续通话与真实 AudioWorklet 流程仍通过。
