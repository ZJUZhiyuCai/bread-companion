# 通话长尾与声音连续性

2026-11-05，基线 `aa82f78`。本轮保留 DeepSeek Flash、同理心提示词、完整候选校验与 MiniMax HD 温暖闺蜜，减少请求往返和播放排队中的空隙。

## 改动

普通倾听电话从“上传转写 → 浏览器收到文字 → 请求模型与语音”改为“上传录音及有界上下文 → 同一响应依次返回转写、已校验回复、音频”。客户端仍先写入用户原话，核对会话、回合与上下文版本后才接受回复。普通聊天只需一次 POST；复盘、练习、修改过的材料及停止/挂断指令仍回到原控制流程。

快照上限为 64 kB、28 条消息、12 条来源，长期明确偏好单独保留。服务器不获得保存、确认材料或切换模式的权限。ASR、模型和 TTS 继续分别准入、计量、超时和去重。只有明确的旧接口 404/405/415 才走兼容路径；不因超时、502 或截断重放整条付费链路。打断与挂断会取消正在上传、生成或播放的回合，迟到结果无法续播。

声音仍是原来的 MP3。服务器把最初的小片段合成至少 16 kB 的首包（128 kbit/s 下约一秒声音），再持续转发，不修改音频样本；短回复正常结束时直接发出。浏览器仅首段预留 60 ms，后续到齐的片段沿上一段的结束时间排队，避免每段重新加 60 ms 而留下间隙。极端网络断流仍可能耗尽缓冲。

两项维护开关分别为 `BREAD_CALL_PIPELINE=off`、`BREAD_SPEECH_START_BUFFER=off`。前者停止向新页面公告合并请求能力；旧页面仍能完成当前请求。开关不改变模型和声音。

## 实测

改动前同一次公网 Chrome 会话的三次等待为 **4.994 / 4.224 / 3.964 秒**（合成语音说完至实际排定播放）。第一轮模型约 2.283 秒；从转写后浏览器发出下一请求到收到候选，另有约 0.6 秒的请求/传输开销。这是减少往返的依据，不是模型耗时可以完全消除的证据。

候选发布前，通过服务器本机入口调用真实 MiniMax / DeepSeek / TTS，结果见 [原始记录](design-detail/candidate-preflight.json)。计时从完整上传请求发起算起，不含浏览器收音与停顿判断，不能直接与上述端到端数字相减。

| 合成输入 | ASR 完成 | 首个音频包 | 回复情况 |
| --- | ---: | ---: | --- |
| “今晚先说说” | 0.773 s | **5.301 s** | 模型耗时 4.160 s，保留这个慢样本 |
| 准备一个月仍被拒，今晚不想听建议 | 0.983 s | 3.043 s | 回应准备与失落，未给建议或追问 |
| 不是想放弃，只是很累，别替我分析 | 0.737 s | 2.890 s | 未把疲惫解释成放弃，尊重暂停 |

三个首包均为 16,749 B。模型与上游网络仍有长尾；这组小样本不能证明所有通话都低于五秒。同理心提示词没有删减，短样本也不能替代广泛的人类评估。

## 发布后的公网验证

已于 2026-11-05 14:36（北京时间）发布 `d36b95a`，PR #31 与 main CI 均通过。本机 3210 / 3215 同步此版本。原始浏览器时序、请求状态、模拟故障、合成回复和对照结果见 [公开记录](evaluation/call-tail-20261105.json)。

一次连续电话经历 12 轮输入，其中第 2 / 7 轮在浏览器分别注入 502 与断网，剩余 10 轮使用真实服务。两次失败后仍使用原来的同一条麦克风轨道继续倾听；中途 75 秒前台静默未发额外请求，之后正常接话，挂断释放麦克风和 AudioContext。10 轮真实回复从说完至排定播放的中位数 **4.413 秒**，最大 **5.990 秒**，其中 2 轮超过 5 秒，片段间最大调度空隙 **0 ms**。单独的真实服务开口打断约 **449 ms**，取消三个已排队片段，下一轮完成。

进一步在同一已部署版本交替启用旧的双请求路径与新的合并路径，每条路径三次、每次新建一通电话。两组均使用相同 DeepSeek、提示词、声音与首包缓冲：

| 浏览器等待 | 旧双请求 | 新合并请求 |
| --- | ---: | ---: |
| 三轮中位数 | **3.983 s** | **4.333 s** |
| 最大值 | 4.505 s | 4.732 s |
| 扣除服务端 ASR / 模型 / 首音频处理后的其余等待中位数 | 1.138 s | 0.984 s |
| 最大音频调度空隙 | 0 ms | 0 ms |

这组对照显示约 **154 ms** 的非供应商处理开销减少，不能说整通等待已稳定变快：新路径这三轮的模型中位耗时更长，掩盖了往返收益。其余等待还包含停顿判断、上传、准入与浏览器排队，并非纯网络 RTT。每组三个样本也不足以估计 P95。**五秒长尾仍未完全消除。**

另外在相同供应商、模型和完整提示词下尝试流式模型响应，仍等待完整 JSON。两次流式完成为 2.029 / 2.054 秒；非流式为 5.379 / 1.522 秒，其中第一次连接未预热。没有稳定提速的证据，因此本轮保留既有模型协议与同理心约束，未引入额外付费并发。

## 回归与前端

本机生产构建通过 **327 项单元/集成测试、70 条浏览器流程**。新增覆盖合并请求的连续通话、取消迟到转写、故障后继续倾听、长上下文、明确偏好、控制指令、流截断及首包边界。重复请求、无访客凭证和跨域请求分别在候选服务返回 409/403/403。

Claude 使用官方 **Opus 5.5 / high** 完成电话色彩与不可用状态、侧栏布局、小屏顶栏、焦点边框及字幕交接；原始 [诊断](design-detail/DIAGNOSIS.md)、[设计实现](design-detail/IMPLEMENTATION.md) 与 [哈希](design-detail/original-sha256.json) 保留。等待提示只在实际等待超过 2.6 秒时出现，不伪造说话或完成状态。11 个状态未发现横向溢出或 serious/critical axe 违规；等待提示出现前后通话按键位移为 0。320 / 390 / 1440px、深色与减少动态的检查见 [浏览器记录](design-detail/browser-layout.json)。

常规 E2E 使用固定媒体和 Mock 服务；真实服务记录使用合成语音与浏览器音频图。实体鸿蒙微信、iOS、蓝牙与外放效果需要设备实测。
